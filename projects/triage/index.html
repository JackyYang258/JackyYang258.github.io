What Does a Self‑Evolved Harness Encode?

Disentangling Language and Model Compensation in Coding Agents

TL;DR Self-evolving harnesses reliably improve coding agents — but what do the evolved artifacts actually contain? We hold one instrumented evolution recipe (TRIAGE) fixed across 8 programming languages × 3 base models on Multi-SWE-Bench and read the answer off the artifacts: an evolved harness is a legible compensation layer that closes the gap between what a model can do and what it does — shaped jointly by the language's engineering demands and the model's behavioral gaps, with a portable disciplinary core and a 20–40% ecosystem-specific remainder that only native re-evolution recovers.

AbstractWhat the paper shows

Self-evolving harnesses are closed-loop systems in which an agent inspects its own rollouts and iteratively edits its prompts, tools, and memory. They reliably improve coding agents in reported evaluations, but prior work reports aggregate gains rather than analyzing what the evolved artifacts encode. It therefore remains unclear whether they encode benchmark-specific adaptations, language-specific engineering knowledge, or compensation for limitations of the underlying model.

We disentangle these factors by holding a single evolution recipe fixed across a grid of eight programming languages (Multi-SWE-Bench) and three base models, and analyzing the resulting harnesses. The recipe routes every edit through a typed failure signal and records it as a falsifiable contract, making each modification attributable after evolution. Four findings emerge. (1) The loop improves held-out solve rates over both a minimal seed and the manually designed mini-SWE-agent scaffold in most cells, with two null regions. (2) Gains compensate recoverable execution defects — where defect mass is near zero, gain is near zero — and which defect dominates is cell-specific. (3) Evolved harnesses share an abstract playbook across languages but instantiate it with almost disjoint language-ecosystem machinery. (4) The shared core transfers and can be distilled into one universal harness, while an ecosystem margin resists both and requires native re-evolution. Together, these results recast the evolved harness as a legible compensation layer, shaped jointly by the language's engineering demands and the model's behavioral gaps, rather than an opaque benchmark-tuned scaffold.

BackgroundWhy ask what a harness encodes?

Coding agents improve for two reasons: the base model gets smarter, or the harness around it gets better. The harness — prompts, tools, memory, workflow scaffolding — is the editable half, and a growing line of work now lets agents evolve it themselves.

Self-evolving harnesses have a strong track record: they beat human-designed baselines and prompt-only self-improvement on standard evaluations. But those results are usually reported in a demonstration setting — one benchmark, one programming language, one base model — as an aggregate score. That leaves a basic question open: when a harness lifts pass@1, what did the loop actually learn? The gain could reflect programming-language knowledge (build systems, test conventions), compensation for the base model's behavioral quirks, or mere overfitting to the evaluated instances. These explanations have very different consequences for whether the harness will transfer to a new language or model.

Distinguishing them is an experimental-design problem, not a bigger-number problem: you have to hold the evolution recipe fixed while independently varying the language and the model, and then analyze the artifacts the loop produces. That is exactly what this paper does, over the code-repair domain of Multi-SWE-Bench: eight languages (Python, Java, C, C++, Go, Rust, JavaScript, TypeScript) × three models (Claude Haiku 4.5, GPT-5-mini, DeepSeek-V4-Flash) — a 24-cell grid, one evolved harness per cell, all produced by the identical recipe.

Language is a particularly clean second axis. Language ecosystems impose concrete, comparable constraints — compilation rules, dependency resolution, test conventions — and fixing the code-repair domain removes task-level variation. Whatever differs between the evolved artifacts of two cells can then be credited to the (language, model) pair itself.

MethodTRIAGE: evolution you can read afterwards

TRIAGE (Typed Routing and Instrumented Attribution for Guided Evolution) is the instrumented evolution loop we hold fixed across the grid. It is deliberately not a new search algorithm — its novelty is placed in legibility: every edit the loop makes remains attributable to a specific failure signal after evolution is done, which is what enables all of the artifact analyses below.

The loop has three properties worth calling out.

Every setting starts from the same minimal seed. The harness is a lightweight plugin layer on mini-SWE-agent exposing four versioned, file-level slots: system prompt, workflow hooks, lessons memory, and tools. Evolution starts from a stripped seed H₀ — a short prompt, one shell tool, empty hooks and memory — so every component beyond the seed must earn its place against measured rollouts. Memory is capacity-bounded and admits only cross-instance-reusable rules, so the cap pressures distillation rather than accumulation.

Attribution uses evidence the agent cannot see about itself. A trajectory records what the agent attempted; a scalar verifier outcome records whether it passed. Neither says why it failed — least of all when the agent believes it succeeded. TRIAGE therefore instruments two extra channels: verifier-side evidence (the scored submission, resulting repository state, and stage-level execution record — which can expose, e.g., a submitted patch silently colliding with the hidden gold test patch) and budget-side evidence (termination reasons and resource use, distinguishing a ceiling-interrupted attempt from a completed-but-wrong one).

Edits are falsifiable contracts, and routing is advisory. The analyzer types each failure (verifier interaction, verification, localization, incorrect repair, efficiency) and hands the evolve agent a dossier — leading cause, failing stages, competing signals — not a verdict. Each proposed edit ships with a prediction of which tasks it should improve; the next round checks the prediction and reverts unsupported changes. A misattribution therefore costs an iteration rather than biasing the harness: the bad edit fails its own contract and is rolled back.

Evaluation: for each language, 20 instances drive evolution and 50 held-out instances are used for testing, with mean_solve@3 over three independent rollouts as the metric, after R = 3 evolution rounds under identical budgets for all compared harnesses.

Finding 1The recipe works — and where it doesn't is explicable

Held fixed across all 24 cells, the loop improves held-out solve rates over the minimal seed in most cells and matches or exceeds mini-SWE-agent in 14 of 24. On Claude Haiku 4.5 the ordering is strict on every non-Python language: evolved > mini-SWE-agent > seed.

The interesting part is where it doesn't work. The two flat regions are not scattered — they fall exactly along the grid's two axes. Along the language axis, Python gains ≈ 0 under all three models. Along the model axis, GPT-5-mini gains little in any language. Both differences lie within rollout standard deviation, so we read them as null results rather than regressions — and both are accounted for by the compensation mechanism of Finding 2, rather than left as unexplained exceptions.

Finding 2Gains are compensation for recoverable execution defects

What does the outer loop actually repair? Overwhelmingly, not the model's understanding of the bug — its process.

We call a defect harness-recoverable when (i) the rollout would plausibly have succeeded had the agent behaved differently at a step it was already capable of executing, and (ii) the corrective can be stated as a rule the harness installs ex ante. Three such defects are frequent enough to detect automatically:

Editing a test file — which collides with the hidden gold test patch and zeroes an otherwise-correct source fix (matched discipline: “never modify test files”). Shipping non-compiling source — so the test executable is never produced (“verify it compiles before submitting”). Submitting without running the target test — so wrong or incomplete fixes go undetected (“run the failing test before submitting”).

This cell-specificity is the operational argument for per-cell evolution — and precisely why a static scaffold falls short: it must hard-code one guess for all cells, while the binding defect shifts with the language.

The two null regions arrive by different routes, one per axis. Python (language axis): for all three models, Python's detector-covered defect rate is the lowest of the eight languages (5.6%) — the rules the loop would install are ones these policies already follow, so evolution has nothing left to buy. GPT-5-mini (model axis): our detectors seldom fire, and the loop reaches the same diagnosis independently — the memory it evolves contains no test-file rule at all, on languages where every other model's harness installs one as its first entry. What remains are localization and repair failures, which no behavioral rule addresses. Notably, GPT-5-mini is not the strongest model in absolute terms — under mini-SWE-agent it is the weakest — suggesting models have qualitative behavioral profiles independent of their capability level.

Scope Within the failure modes we can detect, the gain is compensation, not a raised ceiling: we find no recovered instance where the evolved harness enables a repair the base policy could not otherwise express. A model's measured defect profile is thus a cheap leading indicator of where harness engineering pays off.

Finding 3A shared playbook, almost disjoint instantiations

The main results ship a separate harness per cell. Are these genuinely distinct artifacts, or one generic playbook copied around? We parse each evolved harness into codeable units and tag every unit at two levels: the abstract concept it expresses (“localize from the test output”, “minimal diff”) and any concrete ecosystem marker it names (a build tool, a test-path glob) — then measure cross-language Jaccard overlap at each level.

Harnesses evolved for different languages overlap substantially in what they aim to enforce and almost not at all in how they enforce it. The claim rests on the gap between the two levels rather than on either absolute value: an evolved harness is not a copy of one universal artifact but a partly shared playbook instantiated on the concrete surface of its target ecosystem.

Finding 4Reuse is real — and bounded by the ecosystem margin

If the concept/marker split is functional and not just textual, two predictions follow: stripping the instantiations should preserve the shared part, and transplanting a foreign harness should carry the discipline but the wrong ecosystem. Both experiments confirm it — and they bracket the native ceiling from opposite sides.

Distillation: one universal harness

We aggregate the evolved memory rules of all languages into ten generic guidelines — a memory-only universal harness that names no build command, test path, or file convention — and deploy it unchanged on each language's held-out set (DeepSeek), reporting retention ρ: the fraction of that language's native gain it recovers.

Transplantation: foreign harnesses, unchanged

We then deploy each natively-evolved harness, unchanged, on the other languages' held-out sets (same rollout model in every cell, so differences isolate the harness).

Most of the discipline travels; native remains a ceiling. A harness carried over from an unrelated language recovers a substantial share of the target's gain with no adaptation at all — the behavioral counterpart of the shared concept core, and what makes evolved harnesses useful for bootstrapping a language the loop has never seen. But the shortfall is not confined to weak sources: even the strongest source (C++, row mean 0.95) reaches native on just one of its four targets.

Exporting and importing are different properties. The two marginals are nearly uncorrelated, exactly as the compensation mechanism predicts: a harness exports the discipline matched to its dominant defect, and a target is recoverable only if that is also the defect it exhibits. JavaScript makes the point twice: as a source it exports well into typed targets (C++ 1.32, Go 1.00, Java 0.90); as a target it is the least recoverable language in the matrix (column mean 0.20).

The one wall The single strongly negative cell is JS → TS (−2.30), and it identifies what transfer fails to carry. A JavaScript-evolved harness has the rule “run the failing test before submitting” but no compile-verification step — interpreted JS has nothing to compile. On C++ and Java that omission is harmless: running the tests entails building, so the generic rule silently supplies compile verification. On TypeScript the entailment breaks — test runners routinely transpile without type-checking, so a patch can run its tests green while tsc rejects it, and the grader type-checks. The boundary a portable harness cannot cross is not interpreted-vs-typed as such, but the point where a discipline stops being a free consequence of the ecosystem's own execution chain.

The two experiments agree quantitatively. On ecosystem-heavy targets, the foreign specialized harness beats the stripped universal one yet still falls short of native (universal ≤ transplant < native: C++ 0.65 → 0.90 → 1.0; Java 0.68 → 0.74 → 1.0); on generic targets the order reverses (Go 1.08 vs 0.84; JS 1.13 vs 0.20), the foreign ecosystem baggage being dead weight or worse. The total gain thus decomposes into a large portable disciplinary component and a remainder that neither reuse strategy recovers.

TakeawaysPractical guidance: reuse, distill, or re-evolve?

Read together, the four findings give the compensation picture a quantitative form: the language determines which disciplines a task demands; the model's behavioral profile determines how many of them it already supplies; evolution installs the difference. That yields concrete engineering guidance:

Situation Recommendation Why
Bootstrapping a new language Start from an existing evolved harness or the distilled universal one Transfer is positive in 18/20 ordered pairs; the disciplinary core is language-agnostic
Generic-ecosystem target (e.g. Go, JS) The distilled universal harness is enough Retention ≥ 1.0 — per-language specialization adds nothing where the gain is purely disciplinary
Ecosystem-heavy target (e.g. Java, C++, TS) Native re-evolution is necessary, not optional A 32–52% ecosystem margin resists both transfer and distillation
Deciding whether harness work will pay off at all Measure the model's defect profile first Where detector-covered defect mass is near zero (Python; GPT-5-mini), evolution has nothing to install
Verification steps the ecosystem doesn't enforce for free Name them explicitly in the harness The JS → TS failure: type-checking never happens unless the harness says so

Honest accountingLimitations

Our evidence comes entirely from Multi-SWE-Bench-style tasks: one well-specified repair goal per instance, resolved in a single episode, verified by a fixed test suite — so multi-goal and long-horizon behavior is untested, and persistent memory is exercised only as distilled cross-instance discipline. What counts as a “recoverable defect” is partly defined by the grading protocol: editing a test file is fatal here because the grader applies a hidden gold test patch; two of the three measured defects are protocol-independent, but the magnitude of the first is SWE-Bench-specific. We compare across harnesses under a fixed protocol, which is the reliable quantity.

We do not run head-to-head baselines against related harness-optimization methods (each requires its own evolution budget per cell across a 24-cell grid), and the loop's design elements — diagnostic routing, falsifiable contracts, the non-regression gate — are evaluated as a bundle rather than individually ablated. Splits are small (20 evolution / 50 held-out per language) and evolution runs once per cell, so we interpret aggregate structure — marginals, sign patterns, regime boundaries — rather than single values. Whether the same decomposition into a portable disciplinary component and an ecosystem-bound remainder survives at longer horizons remains open.
